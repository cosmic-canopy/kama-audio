# Gaps found in kama, from building @kama/audio

What this package hits in kama. Each entry is reduced to the smallest program that shows it and **run** on the version
it names. Never edit `../kama` from here: this file is how kama hears about it, relayed by the owner.

**Current compiler:** kama 0.9.966+gca0e88e7, kyoten's pin since 2026-11-17 (bumped on the Windows box, rebuilt on the Mac the same day; 0.9.960 before it, 0.9.956 and 0.9.945 before that; seeded on 0.9.938). KAUD-2, KAUD-7 and KAUD-8 reproduce on it, and two of KAUD-5's three causes stand. KAUD-6 is fixed by KR-332 (0.9.965), and KAUD-1, KAUD-3 and KAUD-4 before it (Retired, below). kama's origin `dev` was still at the pin's commit on 2026-11-17, so nothing past it moves an entry.

Ids are `KAUD-<n>` and are permanent. **Next id: KAUD-9**

| KAUD-2 | GAP | open | **`@noheap` proves no allocation, and a real-time callback also needs to prove it never blocks.** Each of these passes `kama check` inside a `@noheap fn`: a `Locked<int32>` window (`borrow l.lock().value() as v { … }`), `Atomic.wait`, `sleep(d:)`, and `println` (`.scratch/aud-probe-kama/nh/{lock,wait,sleep,print}.kama`). `@noparks` refuses the wait (`noparks.kama`) but still admits a lock window, `sleep` and output (SPEC § the no-parks subset). An audio callback that takes a lock the main thread holds, or sleeps, or writes to a console, misses its deadline and the listener hears a click, and nothing in the language says so. **Why it matters:** this package's render path runs on the device's thread natively and the worklet's on the web, where the browser refuses to block at all (`Atomics.wait` throws in a worklet). The peers state "no allocation, no locks, no I/O" in a C comment. **What already reaches far enough** (2026-11-13, RESEARCH.md § 6.1, `.scratch/aud-probe-ring/contract/`): `@noparks` on the render callback's `fnptr` type follows a call through a contract value, even an `Owned<Processor>` held in a field, into every implementation. It is refused on a contract member, where `@noheap` is accepted. So a no-blocking property placed beside `@noparks` on the callback's type would cover every processor a program hands the engine, with nothing marked on the contract. **The ask:** the reachability property kama's KR-79 already lists ("no blocking syscall (audio/render callbacks)"), as an attribute a callback's `fnptr` type can carry beside `@noheap`, so the whole render path is checked. **Also on the recovery path** (RESEARCH.md § 7.3, `.scratch/aud-probe-device/`): a `@noheap @noparks @onPanic(recover: 1)` render called from CoreAudio's thread recovers a bounds panic and the stream plays on, but the recovered panic's message (*"index 7 is out of bounds for length 4"*) is written from the audio thread, which is output on the real-time path; a real-time callback wants the report kept and handed to the program's thread. Reproduced on 0.9.938 (`0.9.938+g94365be5`), 2026-11-13; the recovery's output on 0.9.943, 2026-11-13; `nh/{lock,wait,sleep,print}.kama` still pass and `noparks.kama` is still refused on 0.9.945 (`0.9.945+gc474b5e9`), 2026-11-13. Still the same on 0.9.949 (`0.9.949+g948759d8`), 0.9.956 (`0.9.956+gdf5a6edf`) and 0.9.960 (`0.9.960+gb39fbaab`), 2026-11-15, and on 0.9.966 (`0.9.966+gca0e88e7`), 2026-11-17. |
| KAUD-5 | GAP | open | **A library cannot carry its consumer's web build when that build needs a second artifact or follows whether the memory is shared.** This package's web leg has two routes (AGENTS.audio.md decision 7, RESEARCH.md § 7.1): on an isolated page one build whose memory is shared, and on any other page the program's build plus a second build of the same program for the AudioWorklet (`ENVIRONMENT=worklet`, `SINGLE_FILE`, `MODULARIZE`, `EXPORT_ES6`, its own entry points). Measured in `.scratch/aud-probe-routes/`, the program had to write all of it: three `select.TARGET`s, one with 8 emscripten settings including an `EXPORTED_FUNCTIONS` list of mangled names (`_routesapp_rw_*`); a `main` per target gated by its own target names; the worklet's `expose fn`s; and four `kama build` runs with their `-o`s. `kama run` serves one artifact, and a `SINGLE_FILE` build is served unisolated. Three things in kama stop the library from carrying it: one `kama build` makes one artifact; no flag says "this build's memory is shared" (kama's KR-327), so a library can neither gate its `emSettings` (which take no gate) nor its kama code on it (its C can, since KR-386, through `__EMSCRIPTEN_WASM_WORKERS__`); and a library's own flag is not its consumer's (KAUD-4). **Why it matters:** every program that plays sound on a page that cannot be isolated would copy this scaffolding, and get its mangled names right by hand. **The ask:** a library can declare a companion artifact of its consumer's program (its own settings and entry points), built by the same `kama build` and served beside it by `kama run`; and a derived flag for shared memory, as `HOSTED` and `SIMD128` are derived. Repro: `.scratch/aud-probe-routes/run.sh`. Reproduced on 0.9.943 (`0.9.943+g590aa28a`), emsdk 7.0.0, macOS arm64, 2026-11-13; unchanged on 0.9.945, which changes no part of a build. **A stream adds a third artifact** (area 4's P8, `.scratch/aud-probe-stream/`, RESEARCH.md § 9.5, 2026-11-14, on 0.9.945): on the page route a decode Worker is the program's own instance again, built `ENVIRONMENT=worker` with its own exported entry points, so the program writes four targets (`WEB_SHARED`, `WEB_WORKLET`, `WEB_DECODER` and the native one) and the worklet's and the decoder's mangled `EXPORTED_FUNCTIONS` lists. **One of its three causes is fixed on the pin:** from 0.9.953, a library's own flag is its consumer's (KAUD-4). The other two stand on 0.9.966, read from kama's commits and its ROADMAP on 2026-11-17: no change from 0.9.946 to 0.9.966 adds a companion artifact to a build, and KR-327's shared-memory flag is still open. |
| KAUD-7 | GAP | open | **A std collection made with a capacity cannot say that its allocator had no room: it traps.** `Deque`, `DynamicArray` and `SlotMap` each take an allocator and a capacity (`withCapacityAndAllocator(allocator:, capacity:)`), and each reserves through `unwrapPtr(o: this.alloc.allocate(…))` (`deque.kama`'s and `slot_map.kama`'s `growTo`, `dynamic_array.kama:105`). The `Allocator` contract answers `None` when it has no room, and `BumpAllocator` does, but the collection turns that `None` into *"kama: panic: out of memory (<prelude>/global.kama:840)"*. A 64-byte `Arena` asked for 1,024 `int64`s: the allocator alone answers `None`; each of the three collections exits 134. No collection has a fallible make or a `tryReserve`, and `try` covers `new` and `cast` only. **Why it matters:** this package declares every capacity and takes its memory from an allocator the program injects (AGENTS.audio.md decision 6), kyoten's an `Arena` sized from a Budget record. At a limit the answer must be declared, never a trap (decision 6; `@kama/gpu`'s decision 9: nothing a program passes ends it). So the backlog in front of the command ring, and later the slot table, cannot use std's `Deque` or `SlotMap`, and the package writes its own fixed storage, as `audio::rt::Ring` already does. **The ask:** a make that can fail, such as `ctor Result<Deque<T, A>, AllocError> tryWithCapacityAndAllocator(allocator:, capacity:)` or a `fn bool tryReserve(n:)`, on each collection that takes an allocator, so a declared capacity drawn from an arena can answer *no room*. Repro: `.scratch/kaud7/` (`kama build kama.json -o out/kaud7`, then `out/kaud7 fallible`, `deque`, `array`, `slotmap`). Reproduced on 0.9.960 (`0.9.960+gb39fbaab`), macOS arm64, 2026-11-15, and still on 0.9.966 (`0.9.966+gca0e88e7`), 2026-11-17: `deque`, `array` and `slotmap` each panic "out of memory" and exit 134. |
| KAUD-8 | BUG | open | **`try new(allocator:)` into a `Shared` traps when the object fits and its control block does not.** SPEC § *`try new` — non-panic construction* calls it "the single fallible construction entry", yielding `None` "when the allocation fails, instead of panicking", and names `Optional<Shared<…>>` among its destinations. It draws the object from the allocator through `ptrOrNull`, which can answer `None`. Then `Shared.adoptIn` draws the 16-byte control block through `unwrapPtr` (`lib/std/memory/shared.kama`, the same at kama's dev, 0.9.964), which panics. From a 64-byte `Arena`'s `BumpAllocator`: a 56-byte object answers *"kama: panic: out of memory (<prelude>/global.kama:840)"* and exits 134; an 8,192-byte object answers `None`, as SPEC says; the same 56-byte object into an `Owned`, which has no control block, is made. So whether `try new` traps depends on how much room is left. **Why it matters:** decision 4 counts each node and buffer the program holds. A `Shared` per node, drawn from the arena the program injects (decision 6), was one way to keep that count (AUD-2). This bug makes it trap at the arena's limit, which decision 6 forbids: a limit's answer must be declared. **The ask:** `adoptIn` draws the control block through the same fallible path, and a `try new` whose second allocation fails gives the first back and answers `None`. Repro: `.scratch/kaud8/` (`kama build kama.json -o out/kaud8`, then `out/kaud8 big`, `seven`, `owned`). Reproduced on 0.9.960 (`0.9.960+gb39fbaab`), macOS arm64, 2026-11-15, and still on 0.9.966 (`0.9.966+gca0e88e7`), 2026-11-17: `big` answers None, `seven` panics "out of memory" and exits 134, `owned` is made. |
