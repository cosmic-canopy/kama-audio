# Gaps found in kama, from building @kama/audio

What this package hits in kama. Each entry is reduced to the smallest program that shows it and **run** on the version
it names. Never edit `../kama` from here: this file is how kama hears about it, relayed by the owner.

**Current compiler:** kama 0.9.956+gdf5a6edf, kyoten's pin since 2026-11-14 (bumped on the Windows box, rebuilt on the Mac on 2026-11-15; 0.9.945 before it; seeded on 0.9.938). KAUD-2 and KAUD-6 reproduce on it, and two of KAUD-5's three causes stand. KAUD-1, KAUD-3 and KAUD-4 are fixed (Retired, below).

Ids are `KAUD-<n>` and are permanent. **Next id: KAUD-7**

| KAUD-2 | GAP | open | **`@noheap` proves no allocation, and a real-time callback also needs to prove it never blocks.** Each of these passes `kama check` inside a `@noheap fn`: a `Locked<int32>` window (`borrow l.lock().value() as v { … }`), `Atomic.wait`, `sleep(d:)`, and `println` (`.scratch/aud-probe-kama/nh/{lock,wait,sleep,print}.kama`). `@noparks` refuses the wait (`noparks.kama`) but still admits a lock window, `sleep` and output (SPEC § the no-parks subset). An audio callback that takes a lock the main thread holds, or sleeps, or writes to a console, misses its deadline and the listener hears a click, and nothing in the language says so. **Why it matters:** this package's render path runs on the device's thread natively and the worklet's on the web, where the browser refuses to block at all (`Atomics.wait` throws in a worklet). The peers state "no allocation, no locks, no I/O" in a C comment. **What already reaches far enough** (2026-11-13, RESEARCH.md § 6.1, `.scratch/aud-probe-ring/contract/`): `@noparks` on the render callback's `fnptr` type follows a call through a contract value, even an `Owned<Processor>` held in a field, into every implementation. It is refused on a contract member, where `@noheap` is accepted. So a no-blocking property placed beside `@noparks` on the callback's type would cover every processor a program hands the engine, with nothing marked on the contract. **The ask:** the reachability property kama's KR-79 already lists ("no blocking syscall (audio/render callbacks)"), as an attribute a callback's `fnptr` type can carry beside `@noheap`, so the whole render path is checked. **Also on the recovery path** (RESEARCH.md § 7.3, `.scratch/aud-probe-device/`): a `@noheap @noparks @onPanic(recover: 1)` render called from CoreAudio's thread recovers a bounds panic and the stream plays on, but the recovered panic's message (*"index 7 is out of bounds for length 4"*) is written from the audio thread, which is output on the real-time path; a real-time callback wants the report kept and handed to the program's thread. Reproduced on 0.9.938 (`0.9.938+g94365be5`), 2026-11-13; the recovery's output on 0.9.943, 2026-11-13; `nh/{lock,wait,sleep,print}.kama` still pass and `noparks.kama` is still refused on 0.9.945 (`0.9.945+gc474b5e9`), 2026-11-13. Still the same on 0.9.949 (`0.9.949+g948759d8`) and 0.9.956 (`0.9.956+gdf5a6edf`), 2026-11-15. |
| KAUD-5 | GAP | open | **A library cannot carry its consumer's web build when that build needs a second artifact or follows whether the memory is shared.** This package's web leg has two routes (AGENTS.audio.md decision 7, RESEARCH.md § 7.1): on an isolated page one build whose memory is shared, and on any other page the program's build plus a second build of the same program for the AudioWorklet (`ENVIRONMENT=worklet`, `SINGLE_FILE`, `MODULARIZE`, `EXPORT_ES6`, its own entry points). Measured in `.scratch/aud-probe-routes/`, the program had to write all of it: three `select.TARGET`s, one with 8 emscripten settings including an `EXPORTED_FUNCTIONS` list of mangled names (`_routesapp_rw_*`); a `main` per target gated by its own target names; the worklet's `expose fn`s; and four `kama build` runs with their `-o`s. `kama run` serves one artifact, and a `SINGLE_FILE` build is served unisolated. Three things in kama stop the library from carrying it: one `kama build` makes one artifact; no flag says "this build's memory is shared" (kama's KR-327), so a library can neither gate its `emSettings` (which take no gate) nor its kama code on it (its C can, since KR-386, through `__EMSCRIPTEN_WASM_WORKERS__`); and a library's own flag is not its consumer's (KAUD-4). **Why it matters:** every program that plays sound on a page that cannot be isolated would copy this scaffolding, and get its mangled names right by hand. **The ask:** a library can declare a companion artifact of its consumer's program (its own settings and entry points), built by the same `kama build` and served beside it by `kama run`; and a derived flag for shared memory, as `HOSTED` and `SIMD128` are derived. Repro: `.scratch/aud-probe-routes/run.sh`. Reproduced on 0.9.943 (`0.9.943+g590aa28a`), emsdk 7.0.0, macOS arm64, 2026-11-13; unchanged on 0.9.945, which changes no part of a build. **A stream adds a third artifact** (area 4's P8, `.scratch/aud-probe-stream/`, RESEARCH.md § 9.5, 2026-11-14, on 0.9.945): on the page route a decode Worker is the program's own instance again, built `ENVIRONMENT=worker` with its own exported entry points, so the program writes four targets (`WEB_SHARED`, `WEB_WORKLET`, `WEB_DECODER` and the native one) and the worklet's and the decoder's mangled `EXPORTED_FUNCTIONS` lists. **One of its three causes is fixed on the pin:** from 0.9.953, a library's own flag is its consumer's (KAUD-4). The other two stand on 0.9.956, read from kama's commits and its ROADMAP on 2026-11-15: no change from 0.9.946 to 0.9.956 adds a companion artifact to a build, and KR-327's shared-memory flag is still open. |
| KAUD-6 | GAP | open | **A wasm release is always built at `-Oz`, and no program can choose speed, so DSP written over views runs 4 to 44 times slower in the browser than the same C at `-O2`.** kama's driver builds every wasm release at `-Oz` (`kama.driver.cpp`: "wasm uses -Oz (size — download cost dominates)"). A target's `cflags` reach emcc before it, so `-Oz` wins: 0.9.945's command line for a target with `"cflags": ["-O3"]` reads `… -O3 -msimd128 -Oz -DNDEBUG …`, and the `.wasm` is byte for byte the same. At `-Oz` the bounds-checked `operator[]` of `View` and `ConstView` is not inlined, so each index is a call. `.scratch/area4/dsp/kernels/` times two kernels, with the same operations in the same order, so every build makes the same bits: a 129-bin complex multiply-accumulate (partitioned convolution's inner loop) takes 4,446 ns over views and 326 ns over raw pointers in an `unsafe fn` at `-Oz`, and 100 and 84 ns when the same emitted C is compiled at `-O2` (natively 18 ns either way). A 256-tap FIR over 128 frames takes 307 µs at `-Oz` and 60 µs at `-O2`. For a whole program, area 4's binaural renderer (`.scratch/aud-probe-spatial/`, RESEARCH.md § 9.1) costs 21 to 24 ms of a core per second of audio per voice at `-Oz` under node, 2.5 to 3.2 at `-O3`, and 2.4 to 2.7 natively. The wasm grows from 76 KB to 101 KB. **Why it matters:** this package's DSP runs in the browser's audio thread, which has 2.67 ms for each 128-frame quantum. At `-Oz`, the browser gets a tenth of the voices native gets from the same code, and no setting changes it. **The ask:** (1) a program chooses a wasm release's optimization, size or speed, as a setting placed after kama's own, so it wins; (2) a library can ask for speed for its hot code only (an attribute on a function or a module), since a library must not impose a program-wide setting. Size stays the default. Repro: `.scratch/area4/dsp/kernels/` built `--release --target WASM_REPRO`, then the same C rebuilt through `.scratch/area4/tools/emcc` with `KAMA_WASM_OPT=-O2`, which swaps the flag and nothing else. Reproduced on 0.9.945 (`0.9.945+gc474b5e9`), emsdk 7.0.0, node 26.13.0, macOS arm64, 2026-11-13. **A long reverb shows it in real time** (area 4's P9, `.scratch/aud-probe-convolver/`, RESEARCH.md § 9.6, 2026-11-14, on 0.9.945): area4dsp's kama `Fft` (over views) takes 3.6 ms for one 16,384-point transform in Chrome's worklet at `-Oz`, more than a 2.67 ms quantum, so a non-uniform convolver on it goes over the period with one reverb and underruns from 8. Offline under node it costs 180 ms of a core per second at `-Oz` and 23 at `-O3`, against 29 natively. The package's long stages use pffft (decision 21) and are not blocked, but no kama FFT can carry them in the browser until a program can choose speed. Still the same on 0.9.949 and 0.9.956, 2026-11-15: the `WASM_O3` target's `-O3` reaches emcc as `-O3 -msimd128 -Oz`. |

| KAUD-1 | BUG | **fixed in 0.9.942 by KR-386**; its repro `aw_tls_nofix/` builds with no workaround on 0.9.943 (`0.9.943+g590aa28a`), 2026-11-13 | **`emSettings` `WASM_WORKERS` does not reach a `csources` file's compile, so a C seam for an AudioWorklet that uses `_Thread_local` or `_Atomic` does not link.** A program with `"emSettings": {"AUDIO_WORKLET": 1, "WASM_WORKERS": 1}` and a `csrc/aw.c` holding `static _Thread_local int32_t per_thread; static _Atomic int32_t counter;` fails at the link: *"wasm-ld: error: --shared-memory is disallowed by …csrc__self__aw.c.o because it was not compiled with 'atomics' or 'bulk-memory' features"*. kama's own objects get the features; the C source does not. It is 0.9.888's defect (a spawning program's `-pthread` moved into the compile flags so `csources` get atomics) again, by the `emSettings` route. **Workaround:** `"cflags": [{"flag": "-sWASM_WORKERS=1", "compileFor": ["ARCH_WASM32"]}]`, with which it builds. **Why it matters:** emscripten's Wasm Audio Worklets are the web leg's audio thread, and its C seam is where the ring and the per-thread state live. **The ask:** a setting that makes the memory shared (`WASM_WORKERS`, `AUDIO_WORKLET`, `SHARED_MEMORY`) adds the matching compile flag to every C source, as `-pthread` does. Repro: `.scratch/aud-probe-kama/aw_tls_nofix/` (fails) and `aw_tls/` (the workaround), `kama build <dir>/kama.json --target WASM`. Reproduced on 0.9.938 (`0.9.938+g94365be5`) with emsdk 7.0.0, macOS arm64, 2026-11-13. |
| KAUD-3 | BUG | **fixed in 0.9.945 by `24991dab`** (each allocation fact filed under the body that wrote it, whatever stack address its buffer had); `sweep.sh` passes all 21 names on 0.9.945 (`0.9.945+gc474b5e9`) and still fails 2 on 0.9.943, 2026-11-13 | **The same program's `@noheap` verdict depends on how its manifest's path is spelled.** `kama check .scratch/aud-probe-cmd/kama.json --target WASM`, run from `kama-audio/`, fails: *"prelude/global.kama:14:0: error: heap allocation (a deep `copy` of `string` allocates a new buffer) is forbidden here — `cmdprobe::render` is `@noheap`"*. The absolute path, `kama.json` from inside the folder, and the same folder reached through 19 other names (symlinks such as `a/`, `y/aud-probe-cmd/`, `deep/a/b/`) all pass, from any working directory. Only names ending `scratch/aud-probe-cmd` and `.scratch/aud-probe-cmd` fail, every time. Line 14 is `Optional`'s `@generate(Equatable, Hashable, Formattable)`. `render` reaches only `Optional<Msg>`'s `match`, never its `Formattable`, so the refusal is false. That points to an analysis whose walk order follows a hash of the path. A reduced program (the ring, the engine and `render` alone) passes under every name, so it is not yet minimal. **Why it matters:** a check that passes on one machine fails in CI, or on another checkout's path, for the same files. A `@noheap` render path is this package's whole real-time guarantee. **The ask:** a verdict that does not depend on the path, and the false refusal found. Repro: `.scratch/aud-probe-cmd/` (the program) and `.scratch/kaud3/sweep.sh <dir> --target WASM`, which checks one project through 21 names (pass 19, fail 2). Reproduced on 0.9.943 (`0.9.943+g590aa28a`, pass 19, fail 2), 0.9.940 and 0.9.938, macOS arm64, 2026-11-13. |
| KAUD-4 | BUG | **fixed in 0.9.953 by KR-390** (`54b44d61`, one flag universe); its repro builds with no re-declaration on 0.9.956 (`0.9.956+gdf5a6edf`), the pin, 2026-11-15 | **A library that gates its code on a flag it declares itself passes its own check, but every consumer's build fails, with an error that names no file.** `lib/kama.json` declares `"flags": { "AUDIO_WORKLET_INSTANCE": {} }` and `lib/src/which.kama` has `@compileFor(AUDIO_WORKLET_INSTANCE) fn int32 which() { return 1; }` and its `!` twin. `kama check lib/kama.json` is OK.
