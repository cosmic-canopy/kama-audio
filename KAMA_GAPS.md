# Gaps found in kama, from building @kama/audio

What this package hits in kama. Each entry is reduced to the smallest program that shows it and **run** on the version
it names. Never edit `../kama` from here: this file is how kama hears about it, relayed by the owner.

**Current compiler:** kama 0.9.940+g1873bcda (kyoten's pin since 2026-11-13; seeded on 0.9.938). KAUD-1 and KAUD-2 reproduce on both.

Ids are `KAUD-<n>` and are permanent. **Next id: KAUD-4**

## Open

| id | kind | status | what |
|---|---|---|---|
| KAUD-1 | BUG | open | **`emSettings` `WASM_WORKERS` does not reach a `csources` file's compile, so a C seam for an AudioWorklet that uses `_Thread_local` or `_Atomic` does not link.** A program with `"emSettings": {"AUDIO_WORKLET": 1, "WASM_WORKERS": 1}` and a `csrc/aw.c` holding `static _Thread_local int32_t per_thread; static _Atomic int32_t counter;` fails at the link: *"wasm-ld: error: --shared-memory is disallowed by …csrc__self__aw.c.o because it was not compiled with 'atomics' or 'bulk-memory' features"*. kama's own objects get the features; the C source does not. It is 0.9.888's defect (a spawning program's `-pthread` moved into the compile flags so `csources` get atomics) again, by the `emSettings` route. **Workaround:** `"cflags": [{"flag": "-sWASM_WORKERS=1", "compileFor": ["ARCH_WASM32"]}]`, with which it builds. **Why it matters:** emscripten's Wasm Audio Worklets are the web leg's audio thread, and its C seam is where the ring and the per-thread state live. **The ask:** a setting that makes the memory shared (`WASM_WORKERS`, `AUDIO_WORKLET`, `SHARED_MEMORY`) adds the matching compile flag to every C source, as `-pthread` does. Repro: `.scratch/aud-probe-kama/aw_tls_nofix/` (fails) and `aw_tls/` (the workaround), `kama build <dir>/kama.json --target WASM`. Reproduced on 0.9.938 (`0.9.938+g94365be5`) with emsdk 7.0.0, macOS arm64, 2026-11-13. |
| KAUD-2 | GAP | open | **`@noheap` proves no allocation, and a real-time callback also needs to prove it never blocks.** Each of these passes `kama check` inside a `@noheap fn`: a `Locked<int32>` window (`borrow l.lock().value() as v { … }`), `Atomic.wait`, `sleep(d:)`, and `println` (`.scratch/aud-probe-kama/nh/{lock,wait,sleep,print}.kama`). `@noparks` refuses the wait (`noparks.kama`) but still admits a lock window, `sleep` and output (SPEC § the no-parks subset). An audio callback that takes a lock the main thread holds, or sleeps, or writes to a console, misses its deadline and the listener hears a click, and nothing in the language says so. **Why it matters:** this package's render path runs on the device's thread natively and the worklet's on the web, where the browser refuses to block at all (`Atomics.wait` throws in a worklet). The peers state "no allocation, no locks, no I/O" in a C comment. **What already reaches far enough** (2026-11-13, RESEARCH.md § 6.1, `.scratch/aud-probe-ring/contract/`): `@noparks` on the render callback's `fnptr` type follows a call through a contract value, even an `Owned<Processor>` held in a field, into every implementation. It is refused on a contract member, where `@noheap` is accepted. So a no-blocking property placed beside `@noparks` on the callback's type would cover every processor a program hands the engine, with nothing marked on the contract. **The ask:** the reachability property kama's KR-79 already lists ("no blocking syscall (audio/render callbacks)"), as an attribute a callback's `fnptr` type can carry beside `@noheap`, so the whole render path is checked. Reproduced on 0.9.938 (`0.9.938+g94365be5`), 2026-11-13. |
| KAUD-3 | BUG | open | **The same program's `@noheap` verdict depends on how its manifest's path is spelled.** `kama check .scratch/aud-probe-cmd/kama.json --target WASM`, run from `kama-audio/`, fails: *"prelude/global.kama:14:0: error: heap allocation (a deep `copy` of `string` allocates a new buffer) is forbidden here — `cmdprobe::render` is `@noheap`"*. The absolute path, `kama.json` from inside the folder, and the same folder reached through 19 other names (symlinks such as `a/`, `y/aud-probe-cmd/`, `deep/a/b/`) all pass, from any working directory. Only names ending `scratch/aud-probe-cmd` and `.scratch/aud-probe-cmd` fail, every time. Line 14 is `Optional`'s `@generate(Equatable, Hashable, Formattable)`. `render` reaches only `Optional<Msg>`'s `match`, never its `Formattable`, so the refusal is false. That points to an analysis whose walk order follows a hash of the path. A reduced program (the ring, the engine and `render` alone) passes under every name, so it is not yet minimal. **Why it matters:** a check that passes on one machine fails in CI, or on another checkout's path, for the same files. A `@noheap` render path is this package's whole real-time guarantee. **The ask:** a verdict that does not depend on the path, and the false refusal found. Repro: `.scratch/aud-probe-cmd/` (the program) and `.scratch/kaud3/sweep.sh <dir> --target WASM`, which checks one project through 21 names (pass 19, fail 2). Reproduced on 0.9.940 (`0.9.940+g1873bcda`) and 0.9.938, macOS arm64, 2026-11-13. |
